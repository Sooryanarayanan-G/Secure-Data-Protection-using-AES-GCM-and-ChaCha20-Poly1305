CS6530 · Applied Cryptography · Assignment 1

Secure Data Protection using AES-GCM and ChaCha20-Poly1305

A design-decision reference for the sender/receiver AEAD subsystem in this repository — what was built, the reasoning behind each choice, and the alternatives that were on the table but not taken.

01 What this project is

The codebase simulates two parties — a Sender and a Receiver — exchanging small structured messages (Records) over a channel that cannot be trusted to preserve confidentiality or integrity. Rather than inventing a cryptographic primitive, the assignment's point is secure engineering: correctly composing an existing AEAD primitive (AES-128-GCM or ChaCha20-Poly1305, both via OpenSSL's EVP API) into a protocol that also handles nonce management, associated data, and replay — the parts that don't come for free just because you called EVP_EncryptUpdate.

Why it matters

Most real-world crypto failures aren't broken ciphers — they're broken protocol logic around a correct cipher: reused nonces, unauthenticated headers, replayed messages, or errors that leak plaintext before verification finishes. This project's structure exists specifically to force those decisions into the open.

02 Architecture at a glance

Five small classes, each owning exactly one concern, wired together by two orchestrators.

ClassOwnsDeliberately does not know about
RecordThe message shape: id, timestamp, payloadBytes, encryption, files
SerializerFixed-width Record ⇄ byte encodingCryptography

SenderBuild record → serialize → encrypt → write channelHow encryption or serialization work internally
ReceiverRead channel → decrypt → verify → replay-check → deserializeHow encryption or serialization work internally
Why this layering

The alternative — one class that reads a string, encrypts it, and writes a file — would be shorter, but it collapses "what is a message" (a domain concept) into "how is it protected" (a cryptography concept). Keeping Crypt ignorant of Record means the AEAD engine is independently testable and reusable for any byte blob, which is exactly what test_suite.cpp exploits by calling Crypt::Encrypt/Decrypt directly for the performance benchmarks, bypassing serialization entirely.

03 End-to-end data flow

What happens between sender.Send("hello") and the string reappearing at receiver.Receive().

  1. Build the record. Sender::CreateRecord assigns the next sequence id (a process-wide monotonic counter) and the current timestamp. Record{ recId, timestamp, data }
  2. Serialize. Serializer::Serialize packs timestamp and data into a fixed-width byte layout — not a raw memcpy of the struct, because struct layout isn't portable across compilers/platforms. [8B timestamp][4B length][N bytes payload]
  3. Split off the AAD. The record id is not serialized into the payload — it's encoded separately via GetAADBytes() and fed to the cipher as Associated Data instead of as plaintext.
  4. Encrypt. Crypt::Encrypt generates a fresh random nonce, runs the selected AEAD cipher over the serialized bytes with the AAD bound in, and returns ciphertext + tag.
  5. Frame the wire format. The four artifacts are concatenated into one blob. secureStream = AAD(4B) || nonce(12B) || ciphertext || tag(16B)
  6. Cross the channel. Sender writes the blob to tm.bin — standing in for a socket, queue, or disk handoff.
  7. Parse the wire format. Crypt::Decrypt slices the blob back into AAD / nonce / ciphertext / tag using the same fixed offsets.
  8. Decrypt + authenticate. The cipher recomputes the tag over the ciphertext and AAD and compares it to the received tag before releasing any plaintext. Mismatch → exception, nothing returned.
  9. Check for replay. Receiver decodes the recId from the now-trusted AAD and rejects it if that id has been accepted before.
  10. Deserialize. Serializer::Deserialize turns the verified plaintext back into a Record, which Receiver::Receive hands back as a plain string.

04 AEAD, from first principles

Why the assignment insists on AEAD specifically, rather than "encryption" in general.

Plain encryption (e.g. AES-CTR alone) gives confidentiality but not integrity — an attacker who can't read the plaintext can still flip bits in the ciphertext and produce a predictably corrupted plaintext on the other end, which is exactly how bit-flipping attacks against unauthenticated stream ciphers work. The historical fix was to bolt a MAC onto an encryption scheme, and there are three ways to combine them:

Composition strategies for confidentiality + integrity
SchemeMAC computed overKnown weakness
Encrypt-and-MACPlaintextMAC can leak plaintext info (used in SSH); doesn't guarantee ciphertext integrity
MAC-then-EncryptPlaintext, then MAC+plaintext both encryptedPadding-oracle attacks (the class of bug that broke early TLS/SSL CBC modes)
Encrypt-then-MACCiphertextProvably secure if done correctly, but easy to implement wrong (nonce reuse, MAC omitted on associated data)
AEAD (GCM / Poly1305)Ciphertext and unencrypted associated data, as one atomic primitiveStill fails badly on nonce reuse — but there's only one primitive to get right, not two composed independently
Why AEAD won

AEAD collapses "encrypt correctly" and "MAC correctly, over the right data, without leaking a timing oracle" into a single library call, which is precisely what the assignment brief means by "the emphasis is on correctly integrating these algorithms" rather than composing primitives by hand.

05 AES-128-GCM internals

What EVP_aes_128_gcm() is actually doing.

GCM (Galois/Counter Mode) is AES run in CTR mode for encryption — the block cipher generates a keystream by encrypting a counter derived from the nonce, and that keystream is XORed with plaintext, making it a stream cipher built from a block cipher. Authentication is layered on top via GHASH, a universal hash function over GF(2¹²⁸) that processes the AAD and ciphertext to produce the tag. This is why the OpenSSL calls for AES-GCM look almost identical to a stream cipher API (EVP_EncryptUpdate for data, a separate _ctrl call to fetch the tag) rather than a block-padding API.

Alternative AES-based AEAD modes not used here
ModeTradeoff vs GCM
GCM (chosen)Hardware-accelerated on any CPU with AES-NI + PCLMULQDQ; the de facto default (TLS 1.3, IPsec, SSH)
CCMNo hardware GHASH acceleration; two passes over the data (CBC-MAC then CTR) — used mainly in constrained IoT (802.15.4/Zigbee)
SIV (Synthetic IV)Nonce-misuse resistant — safe even if a nonce repeats — but requires two passes and isn't part of the standard EVP one-shot streaming API
AES-CBC + HMAC (manual)What GCM replaced; requires the encrypt-then-MAC discipline above, and CBC needs padding, opening padding-oracle risk

06 ChaCha20-Poly1305 internals

Why the assignment asks for a second, structurally different algorithm rather than a second AES mode.

ChaCha20 is a pure software stream cipher — it never needs a lookup table or dedicated silicon to run at speed, because it's built entirely from add-rotate-XOR (ARX) operations on 32-bit words. That also makes it inherently free of the cache-timing side channels that plagued naive AES table-lookup implementations before AES-NI existed. Poly1305 is a polynomial MAC evaluated in GF(2¹³⁰−5) rather than GF(2¹²⁸) — a completely different mathematical construction from GHASH, computed once per message from a one-time key derived from the ChaCha20 keystream's first block (RFC 8439's construction, which is what OpenSSL's EVP_chacha20_poly1305() implements).

Why it's the second algorithm here

The assignment wants a genuine comparison, not two flavors of the same design. AES-GCM depends on hardware acceleration to be fast and constant-time; ChaCha20-Poly1305 is fast and constant-time everywhere, including phones and embedded cores without AES-NI. That's a real, measurable engineering tradeoff — see §14 — not just a policy choice.

07 Wire format design

Why AAD || nonce || ciphertext || tag, concatenated with fixed widths, instead of something more self-describing.

Offset  0        4              16                   len-16        len
        +--------+--------------+--------------------+-------------+
        | AAD    | nonce        | ciphertext          | tag         |
        | 4 bytes| 12 bytes     | variable             | 16 bytes    |
        +--------+--------------+--------------------+-------------+
Framing alternatives considered
ApproachTradeoff
Fixed-width concatenation (chosen)Zero parsing ambiguity, no extra bytes spent on length prefixes — but only works because every field except ciphertext has a length fixed by the algorithm choice
Length-prefixed TLVSelf-describing and extensible (can add fields later without breaking old parsers) — costs a few bytes per record and a bit more parsing code; the standard choice for a real wire protocol
Structured envelope (protobuf / JSON+base64)Versionable and language-agnostic, natural if sender/receiver were separate services — pure overhead for a single-process file handoff
Out-of-band headerAAD/nonce sent via a separate channel or fixed protocol field (this is what TLS records and IPsec ESP actually do) — avoids re-deriving offsets, but there's no "protocol field" to reuse here

The fixed-width scheme is only safe because the ciphertext is the last variable-length field before a fixed-length tag — if two variable-length fields existed, positional slicing would be ambiguous and a length prefix would become mandatory.

08 Nonce management

FR-5 / SR-3: correctly manage nonces, and never reuse one with the same key.

Crypt::GenerateNonce draws a fresh 96-bit value from RAND_bytes (OpenSSL's CSPRNG) for every single call to Encrypt — nothing is cached or derived from a counter. This is the standard, simplest-to-get-right nonce strategy for both GCM and ChaCha20-Poly1305, which is why both ciphers standardize on a 96-bit nonce in the first place.

Nonce strategies compared
StrategyReuse riskCost
Random 96-bit (chosen)Birthday-bound collision risk grows past ≈2³² messages under one keyNone — no shared state between sender calls
Monotonic counterZero collision risk by construction, if state is durableSender must persist the counter across restarts, or a crash-and-reuse bug silently breaks security
XChaCha20-Poly1305 (192-bit nonce)Random nonces become safe up to ≈2⁹⁶ messages — the birthday bound moves out of reachNot in the assignment's two required configurations; would need a different EVP cipher (EVP_chacha20_poly1305 doesn't have an X-variant in stock OpenSSL 3.x)
Partitioned counter (multi-sender)Zero risk across senders sharing a key, via a fixed sender-id prefix + local counterExtra coordination/allocation of the id space; the pattern used by QUIC and IPsec SAs
Why random over counter

A counter is safer in the limit but only if it survives a crash — get that wrong and you get catastrophic, silent nonce reuse. Random nonces degrade gracefully (the risk is probabilistic and bounded, not a hard failure mode) and need zero persisted state, which matches the assignment's message volume (TR-7 asks for ~10,000 records — nowhere near the 2³² birthday bound) far better than the operational complexity a durable counter would add for a demo subsystem.

test_suite.cpp's TR-7 test empirically checks this: it sends 10,000 records under one key and collects every nonce into a std::set, asserting the set's size stays at 10,000 (i.e., zero collisions observed).

09 Associated Data design

FR-4 / SR-4: what gets authenticated but not encrypted, and why it's just the record id.

The 4-byte record id is bound into the tag as AAD via Serializer::GetAADBytes. It stays visible in plaintext on the wire (record ids usually aren't secret) but can't be detached from its ciphertext or swapped for another record's id without invalidating the tag.

What could have been chosen as AAD
AAD contentWhat it protectsCost
Record id only (chosen)Binds ciphertext to its sequence position — enables replay detectionMinimal; 4 bytes
No AADNothing beyond the payload itselfCheapest, but nothing stops a valid ciphertext from being replayed under a different apparent sequence number
Full header (id + timestamp + sender identity)Also authenticates freshness and origin, closer to what a real transport protocol (e.g. a TLS record header) authenticatesMore AAD bytes to transmit in the clear; timestamp freshness checks need clock-sync assumptions this assignment explicitly places out of scope
Application-level context (e.g. session id, channel id)Prevents cross-context ciphertext splicing when one key is shared across multiple logical streamsNot applicable — this design uses one key per Crypt instance / one logical channel

10 Replay protection

FR-8 / SR-5 / TR-5 — the piece that was entirely missing before this session's changes.

Receiver keeps a std::set<uint32_t> seenRecIds. After a record decrypts and authenticates, its id (recovered from the now-trusted AAD) is checked against the set; a repeat is rejected before Receive() ever returns data.

Replay-detection strategies compared
StrategyHandles out-of-order delivery?Memory profileReal-world analogue
Seen-id set (chosen)Yes — any id, any order, exactly onceUnbounded — grows with every accepted record for the session's lifetime—
Monotonic counter (reject id ≤ last seen)No — legitimately reordered records are also rejectedO(1) — a single integerNot standard alone; usually paired with a window (below)
Sliding window (accept a bounded range, bitmap for the window)Yes, within the window widthO(window size) — bounded and smallTLS 1.3 record replay window; IPsec ESP anti-replay window
Timestamp freshness (reject if outside ±Δ of now)Yes, within ΔO(1) if combined with a short-lived seen-cacheKerberos ticket freshness; needs synchronized clocks
Why an unbounded set, here

A sliding window is the production-grade answer — it's what TLS and IPsec actually ship, because an unbounded set is a memory-exhaustion liability over a long-lived connection. It was skipped here because the assignment's scope is a session-bounded demonstration (thousands of records, not an always-on service), and a plain set makes the correctness property — "no id is ever accepted twice" — visually obvious in the code and trivial to verify in TR-5, rather than being an artifact of a window size choice.

Worth flagging in the report

This is a legitimate scoping tradeoff to name explicitly in the Assignment 1 Report's Discussion section — "unbounded seen-set, sufficient for this demonstration's message volume; a sliding window would be required for a long-running service" is exactly the kind of documented assumption FR-10 asks for.

11 Authentication-failure handling

FR-7 / SR-6 — reject bad records without ever releasing recovered plaintext.

OpenSSL's decrypt API is asymmetric on purpose: EVP_DecryptUpdate will happily emit some bytes even for a tampered ciphertext — the tag check only happens at EVP_DecryptFinal_ex, which returns ≤0 on mismatch. Crypt::Decrypt treats that as the single point of truth and throws std::runtime_error rather than returning a flag, which forces every caller up the chain to either handle the failure explicitly or let the record be dropped — there's no code path where a caller can accidentally read the reference-passed plainText buffer after a failed verification, because the exception unwinds before Receiver::ConstructRecord reaches the line that would use it.

Why exceptions over a return code

A boolean/error-code return is easy to silently ignore (if (ok) { ... } without an else is a compiling, plausible-looking bug). An uncaught exception crashes loudly; a caught one forces a conscious decision at the catch site. Receiver::ConstructRecord's catch (...) is that conscious decision — "any failure in this block means reject the record," which is the fail-closed posture SR-6 requires.

12 Key management — explicitly out of scope

The assignment states the sender and receiver already share a secret key; this project reads that key from a file.

keys/aeskey.bin (16 bytes) and keys/ccpkey.bin (32 bytes) are read raw from disk by main.cpp's GetKey. For context — not because it needed implementing here — real systems get that shared key one of a few ways:

Pre-shared key (used here)

Provisioned out-of-band before any communication. Simple, but doesn't scale past a small, fixed set of parties and has no forward secrecy if the key ever leaks.

Key exchange (Diffie–Hellman / X3DH)

Derives a fresh shared secret per session over an insecure channel. What TLS and Signal actually do; explicitly named as a later-course topic in the assignment brief.

KDF from a master secret

One long-term key plus HKDF derives per-purpose subkeys (e.g. separate keys for AES-GCM vs ChaCha20 configurations) — avoids ever reusing raw key material across algorithms.

KMS / HSM-backed key

Key material never leaves a hardware boundary; the application calls an API to encrypt/decrypt rather than holding raw bytes. Standard for production cloud services.

13 Testing strategy

How test_suite.cpp demonstrates TR-1 through TR-8 without a real network.

The assignment allows the three logical roles (sender, malicious actor, receiver) to live inside one process, "provided that all Functional and Testing Requirements are satisfied." test_suite.cpp takes that option: the "malicious actor" is a function that opens tm.bin after a legitimate Send() and flips one byte at a computed offset — position 16 for ciphertext (TR-2), the final byte for the tag (TR-3), byte 0 for the AAD (TR-4).

Why byte-flip a file instead of a real MITM

A genuine network-level attacker would intercept a socket write; flipping a byte in the shared file achieves the identical adversary model — "the attacker can modify bytes in transit" — without the assignment's added complexity of standing up sockets or processes, which the brief explicitly says isn't required ("network communication is optional").

Scoping note for TR-8

Performance is measured on Crypt::Encrypt/Decrypt directly, bypassing Sender/Receiver's file I/O. Going through the full file-based pipeline would work too, but disk I/O time would dominate and mask the actual cost difference between the two ciphers — worth stating as an assumption in the report.

At 64 bytes the two are within noise of each other — fixed per-call overhead (context setup, a handful of AES/ChaCha rounds) dominates at that size, not the cipher's steady-state throughput. By 1 KiB and clearly by 64 KiB, AES-128-GCM pulls roughly 2× ahead.

Why AES-GCM wins on this machine

This CPU has AES-NI and PCLMULQDQ instructions — dedicated silicon that does one AES round or one GHASH multiply per instruction. ChaCha20-Poly1305 has no equivalent hardware fast path; it runs as general-purpose ARX/polynomial arithmetic on the ALU regardless of what CPU it's on. That's precisely the tradeoff named in §6: on a CPU without AES-NI — many low-end ARM cores, some older mobile chips, some embedded/IoT targets — this result inverts and ChaCha20-Poly1305 wins, which is the whole reason it exists as a TLS 1.3 cipher suite alongside AES-GCM rather than as a replacement for it.

16 Limitations & what production hardening would add

  • Unbounded replay set — see §10; a sliding window bounds memory for long-lived sessions.
  • No key rotation or expiry — a static key file has no mechanism to retire compromised key material.
  • No transport authentication of the channel itself — tm.bin has no access control; a real deployment needs the channel (socket, queue) secured or the threat model explicitly scoped to "ciphertext-only visibility," which the AEAD tag already defends against.
  • Single-threaded, single-session assumptions — Sender::sendCount is a process-wide static counter; a multi-sender system sharing one key would need the partitioned-nonce scheme from §8 to keep nonce spaces disjoint.

None of these are bugs relative to the assignment's stated scope (§3.2 of the brief explicitly excludes key exchange, PKI, and transport-layer protocols) — they're the documented assumptions the Assignment 1 Report's Discussion section is asking for.
